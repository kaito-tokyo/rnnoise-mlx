# MLX CUDA graph reconstruction investigation

Investigation date: 2026-09-20. Application HEAD: `023b523`.
No training code or production runtime was changed.

## Conclusion

The observed CUDA graph node reconstruction is an explicit backend policy,
including on executable-graph cache hits. It is not evidence by itself of
`mx.compile` retracing, JIT recompilation, or unstable graph topology.
The backend builds a new graph, looks up a cached executable by topology,
updates that executable, launches it, and starts another fresh graph.

The main source of graph fragmentation is the small encoder limit combined
with the large primitive graph generated by time-unrolled GRUs and autodiff.
Moving the optimizer inside `mx.compile` does not remove this backend policy.

## Source call path

Paths and line numbers below refer to the local MLX checkout unless stated.

1. Application `colab/profile_train.py:59` calls
   `CUDATrainingLoop.run_update`; `training_cuda/loop.py:44` compiles the whole
   update, and line 114 evaluates its roots. The eight chunks are inside the
   compiled function; there is no explicit `mx.eval` inside its chunk loop.
   The separate `training/train.py:558` entry uses `CompiledChunkRunner`.
   This establishes both source entry paths, not the historical trace's
   exact command line, which is not recorded in the handoff.
2. `python/mlx/nn/layers/recurrent.py:167`: GRU loops over each time index.
   Each step slices gates and performs `hidden @ self.Wh.T` (line 170).
   Three GRUs x 250 frames x eight chunks = 6,000 recurrent forward steps
   per update, before backward operations. They are expanded into array
   operations, not represented as one fused recurrent CUDA kernel.
3. `mlx/compile.cpp:78`: fusion accepts selected unary/binary/ternary and
   broadcast operations. Matmul and Slice/SliceUpdate are not in that set.
   Fusion also has depth/array limits (lines 24-25). A whole compiled Python
   update therefore still contains many backend primitives.
4. `mlx/backend/cuda/compiled.cpp:225`: `Compiled::eval_gpu` obtains a cached
   JIT module, allocates outputs as needed, and adds a kernel node. Its NVTX
   count measures evaluations of fused primitives, not compiler invocations.
5. `mlx/backend/cuda/eval.cpp:73`: after evaluating each primitive, check
   `encoder.needs_commit()`. `device.cpp:181` supplies default limits of
   20 nodes and 100 MB for devices without a special case, including T4.
   `device.cpp:458` checks **strictly greater than** either limit. A primitive
   can add several nodes before this check, so graphs can exceed 21 nodes.
   The byte counter accumulates input `data_size()` values, including repeat
   uses; it is not the unique live allocation size. Finalize also commits.
6. `device.cpp:499`: commit uses a node-type/dependency key and an LRU cache
   (default capacity 400). A hit attempts `cudaGraphExecUpdate`; a failed
   update resets the executable and causes instantiate. A miss also
   instantiates. Non-updatable graphs take a separate instantiate path.
   After launch, line 561 clears graph state and constructs a new CudaGraph.
   Thus a cache hit does not bypass graph construction.
7. `cublas_utils.cpp:198`: every cuBLAS matmul execution enters a capture
   context. `device.cpp:71` and `:80` begin/end capture and insert a child
   graph. `subgraph_to_key` queries its nodes twice for a nonempty graph.

## SliceUpdate origin and allocation limits

`mlx/primitives.cpp:5017`, `Slice::vjp`, creates a zeros-like input gradient
and inserts the cotangent through `slice_update`. GRU's per-frame and gate
slices therefore provide a concrete source of backward SliceUpdates; the
final hidden-state extraction is not their only source. Exact attribution
of each SliceUpdate to a particular Python expression remains unmeasured.

`mlx/backend/cuda/indexing.cpp:571` copies the base array, then writes the
slice. The trace has 72,144 SliceUpdate evaluations and 144,288 kernel-node
additions within them: exactly two per evaluation in this run.

The allocation hypothesis in the handoff needs qualification. 30,046 of
43,993 cudaMallocAsync calls are inside Compiled evaluation, whose source
explicitly allocates output buffers. `allocator.cpp:171` tries the MLX buffer
cache before reaching cudaMallocAsync. These events cannot simply be labeled
CUDA graph metadata allocations. cudaMallocManaged calls (28,363) are outside
primitive eval ranges in this trace; their precise callers remain unresolved.
Allocation counts alone do not establish a leak or stable memory consumption.

## Next controlled experiment

Do not move `value_and_grad` outside compile based on the old hypothesis.
First compare the existing baseline with only `MLX_MAX_OPS_PER_BUFFER=100`
changed, in a fresh subprocess because environment values are cached.
Keep the byte limit, batch size 4, 2,000 frames, TBPTT 250, feature identity,
and model initialization fixed. This is a proposed experiment, not a measured
speedup or a configuration change made by this investigation.

Add outer per-update NVTX ranges around `run_update`, outside the compiled
function. The existing trace has no per-update labels, so it cannot reliably
separate setup/compile from updates 1/2/3 using those markers. Compare warmed
update times, loss agreement, node/launch/update/instantiate counts, CPU/GPU
timing and memory. Larger buffers may reduce commit/launch overhead but retain
more temporaries; they do not eliminate node construction or cuBLAS capture.
Use a unique output directory and report completion separately from trace
creation. Production Colab settings remain unchanged.

If node construction still dominates, investigate fused recurrent primitives
or a backend replay strategy with explicit address/lifetime handling. Merely
increasing the executable cache size cannot bypass the unconditional new-graph
construction on cache hits.
